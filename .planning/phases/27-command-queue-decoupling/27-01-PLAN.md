# Phase 27-01: 命令队列解耦 + 锁粒度细化

## Goal

将 Python 后端全局 `asyncio.Lock` 阻塞模式改造为异步命令队列：API 端点异步入队立即返回，后台单 Worker 串行消费执行，保证 ADK 状态安全的同时消除客户端命令阻塞。

## Depends On

- Phase 13 (API Foundation) — REST 端点基座
- Phase 14 (WebSocket Layer) — event_callback 机制

## Success Criteria

1. API 端点 < 50ms 返回 `status=queued` + `command_id`
2. Worker 单协程串行持有 `runner_lock`，ADK 状态安全
3. WS 事件推送随命令入队，执行期间正常推送
4. GET `/drama/command/{id}` 支持轮询命令状态
5. 已完成命令 5 分钟后自动清理，>100 条时触发清理

## Task Breakdown

### 1. 新建 `app/api/command_queue.py`

**`QueuedCommand` dataclass**
- 字段：`id`, `command_text`, `user_id`, `session_id`, `event_callback`, `created_at`, `status`, `result`, `error`, `started_at`, `completed_at`
- `status` 生命周期：`pending` → `running` → `completed | failed`

**`CommandQueue` 类**
- `__init__(runner, lock)`：创建 `asyncio.Queue`，初始化 `_commands` 字典
- `start()`：启动 `_worker_loop()` 后台协程
- `stop()`：发送 sentinel 信号，优雅关闭（5s 超时后 cancel）
- `enqueue(command_text, event_callback)` → `command_id`：立即入队，<50ms 返回
- `get_command(command_id)` → `QueuedCommand | None`：供轮询端点查询
- `queue_depth` → `int`：当前队列深度
- `_cleanup_old_commands(max_age=300)`：清理已完成命令，防止内存泄漏
- `_worker_loop()`：核心循环
  - `queue.get()` 取出命令
  - sentinel 检测优雅退出
  - `status = "running"`，记录 `started_at`
  - `async with self._lock:` 执行 `run_command_and_collect()`
  - 成功 → `completed`，记录 `result`
  - 异常 → `failed`，记录 `error`，通过 `event_callback` 推送 error WS 事件
  - `queue.task_done()`，>100 条时触发 cleanup

### 2. 修改 `app/api/models.py`

**`CommandResponse` 扩展**
- 新增 `command_id: str = ""` 字段（`status=queued` 时填充）

**新增 `CommandStatusResponse`**
- `command_id: str`
- `status: str` — pending | running | completed | failed
- `command_text: str = ""`
- `result: dict = {}`
- `error: str = ""`
- `queue_depth: int = 0`
- `elapsed_seconds: float = 0.0`

### 3. 修改 `app/api/deps.py`

**新增 `get_command_queue`**
- `request.app.state.command_queue` 返回 `CommandQueue` 实例

### 4. 修改 `app/api/app.py` lifespan

**Startup**
- 创建 `CommandQueue(runner, runner_lock)` 并赋值给 `app.state.command_queue`
- 调用 `await command_queue.start()`

**Shutdown**
- 调用 `await command_queue.stop()`

### 5. 改造 `app/api/routers/commands.py`

**新增 `_enqueue_director_command()` 辅助函数**
- 获取 `event_callback`（有 WS 客户端时创建 broadcast callback）
- 调用 `command_queue.enqueue(command_text, event_callback)`
- 返回 `CommandResponse(status="queued", message="命令已入队...", command_id=cmd_id)`

**改造导演模式端点**（全部从 `async with lock` 改为入队）
- `POST /drama/next` → `_enqueue_director_command("/next")`
- `POST /drama/action` → `_enqueue_director_command("/action {description}")`
- `POST /drama/speak` → `_enqueue_director_command("/speak {actor_name} {situation}")`
- `POST /drama/steer` → `_enqueue_director_command("/steer {direction}")`
- `POST /drama/auto` → `_enqueue_director_command("/auto {num_scenes}")`
- `POST /drama/end` → `_enqueue_director_command("/end")`
- `POST /drama/storm` → `_enqueue_director_command("/storm {focus}")`
- `POST /drama/chat` → 普通消息入队；`/cast` 仍直接执行（快操作，无 LLM）

**保持不变**
- `POST /drama/start` — 初始化状态快，STORM 已是后台任务
- `POST /drama/free_chat` — bypass 锁，直联 A2A

**新增轮询端点**
- `GET /drama/command/{command_id}` → `CommandStatusResponse`
  - 查询 `command_queue.get_command(command_id)`
  - 不存在 → 404
  - 存在 → 返回 status、queue_depth、elapsed_seconds
  - `completed` → 附带 `result`
  - `failed` → 附带 `error`

### 6. 测试验证

- [ ] `enqueue()` 立即返回，不持有锁
- [ ] 多命令连续入队，端点响应 < 50ms
- [ ] Worker 串行执行，同一时刻仅一个命令持有 `runner_lock`
- [ ] WS 事件在命令执行期间正常推送
- [ ] `GET /command/{id}` 轮询返回正确状态
- [ ] 命令完成后 `_commands` 字典 5 分钟后自动清理
- [ ] Worker 异常不崩溃，记录日志后继续消费
- [ ] `/start` 和 `/free_chat` 行为不变
- [ ] Linter 0 errors

## Risk & Mitigation

| 风险 | 缓解 |
|------|------|
| Worker 单点故障 | Worker 异常捕获，记录日志后继续消费下一条 |
| 命令堆积 | 队列无上限，但 Worker 单线程保证顺序；客户端可通过 queue_depth 感知 |
| 内存泄漏 | 已完成命令 5 分钟后自动清理，>100 条时触发清理 |
| REST 降级客户端白屏 | 新增 `/command/{id}` 端点供轮询结果 |

## Notes

- Android 客户端无需修改：WS 事件流不变，REST 响应新增 `command_id` 字段不影响现有解析（多余字段被忽略）
- `free_chat` 完全不受影响，仍 bypass 锁直联 A2A
- 查询端点（`/drama/status`, `/drama/scenes` 等）不使用锁，不受影响
